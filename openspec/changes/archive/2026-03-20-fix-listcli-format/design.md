## Context

当前 `aitools list` 命令使用 `String.padEnd()` 手动对齐三列（名称、描述、同步状态），存在以下问题：

1. 中文字符在终端中占 2 个字符宽度，但 `padEnd` 按字符数计算，导致列对不齐
2. 只显示一个"综合同步状态"，用户无法知道具体是哪个目标工具需要更新
3. 没有展示源文件 hash，无法直观判断内容版本

涉及文件：`src/commands/list.ts`（约 160 行）和 `src/types/index.ts`。

## Goals / Non-Goals

**Goals:**

- 使用标准化表格格式输出 list 结果，确保终端对齐正确
- 展示源文件 hash 短值（SHA-256 前 8 位），作为版本标识
- 每个已启用的目标工具独立一列，显示该工具与源文件的对比状态
- 保持现有的错误处理逻辑（配置不存在、源目录为空等）

**Non-Goals:**

- 不引入第三方终端表格库（如 cli-table3），使用手动构建的 Unicode Box Drawing 字符或简单分隔符
- 不改变 hash 计算逻辑（`src/core/hasher.ts` 不变）
- 不改变配置文件格式或扫描逻辑

## Decisions

### 1. 表格渲染方案：手动构建 Unicode 表格

**选择**：使用 `│`、`─`、`┼` 等 Unicode Box Drawing 字符手动拼接表格行。

**替代方案**：引入 `cli-table3` 库 → 排除，因为该变更较小，不值得新增依赖。

**实现**：新增一个 `formatTable` 辅助函数，接收表头和数据行，根据各列最大宽度自动对齐。对中文字符使用 `getStringWidth()` 计算实际终端宽度（每个 CJK 字符宽度为 2）。

### 2. Hash 展示格式：短 hash（前 8 位）

**选择**：截取 SHA-256 hex 的前 8 位字符展示，与 Git short hash 用户心智模型一致。

**原因**：完整的 64 位 hash 太长，会破坏表格布局。8 位足以区分不同版本。

### 3. 状态文案调整

| 状态码 | 旧文案 | 新文案 | 场景 |
|---|---|---|---|
| `synced` | ✅ 已同步 | ✅ 已同步 | 源 hash = 目标 hash |
| `changed` | ⚠️ 有变更 | ⚠️ 需更新 | 源 hash ≠ 目标 hash |
| `not_synced` | ❌ 未同步 | ❌ 未同步 | 目标中不存在该 Skill |

"有变更" 改为 "需更新"，对用户更具操作指引性。

### 4. 列结构

固定列：`Skill 名称`、`源 hash`。
动态列：根据配置中 `enabled: true` 的目标工具动态生成列（如 `CodeBuddy`、`Claude Code`）。

这意味着如果用户只启用了一个工具，表格只有 3 列；两个都启用则 4 列。

## Risks / Trade-offs

- **[宽字符计算]** → 手动实现 `getStringWidth` 函数判断 CJK 字符，已有成熟算法可参考，复杂度可控
- **[终端宽度溢出]** → 当 Skill 名称过长时可能导致表格折行。缓解措施：名称截断到 20 字符 + `...`
- **[性能无影响]** → 仅改变输出格式，hash 计算逻辑不变
