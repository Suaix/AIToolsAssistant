# L2 · 设计原则（Design Principles）

> **这是 4 条可判对错的铁律。**  
> 每次设计评审、每次 PR 审查、每次 AI 生成代码，都要拿这 4 条对照。  
> **符合 = 通过；违反 = 打回。** 不允许"既要又要"。

## 为什么只有 4 条？

**太多会记不住，太少无力挡错。** 4 条是经过权衡的最少必要集——

- **少于 4 条**：覆盖不到"呈现 / 克制 / 隐形 / 信任"全部关键面
- **多于 4 条**：团队记不住，记不住的原则等于不存在
- **每条必须是"A 先于 B"结构**：没有张力的原则都是废话（"设计要美观"谁都知道）

# 原则 1 · 状态先于功能

> **State before Action**

## 📖 内涵

打开任何一个页面，用户最先看到的应当是**"现在的状态"**，而不是**"能做什么操作"**。

状态 = 事实（what is）；功能 = 可能性（what could be）。  
**我们的产品卖"确定性"，不卖"可能性"。** 所以状态必须打头。

## 🎯 L1 依据

- 产品承诺：**"让你永远用到最新版本的自己"** —— 承诺的就是状态
- 情绪曲线：**迷失 → 掌控** —— 掌控的前提是先知道现状
- 用户 Alex：**想一眼看到"都是最新吗"**，而不是"我可以做哪些操作"

## ✅ 正例

- **首页顶部**：一张"全局新鲜度"卡片—— "3 个工具、12 个 Skill、全部最新 ✓"
- **Skill 卡片**：状态徽章在最显眼位置（"已同步 / 需更新 / 未连接"），操作按钮折叠在右侧次要位置
- **同步进行中**：页面标题直接变成 "同步中… (2/5)"，而不是弹窗遮挡
- **文件路径列**：直接显示路径本身，而不是"点击查看路径"

## ❌ 反例

- ❌ 首页顶部是"+ 新建 Skill / + 连接工具 / + 导入资源"三个大按钮（这是"功能"不是"状态"）
- ❌ Skill 卡片标题是 "code-review"，但要展开才能看到同步状态
- ❌ 用弹窗提示"同步完成"后自动消失（用户事后想回看"当时同步了什么"找不到）
- ❌ 侧边栏分组叫"操作 / 管理 / 设置"（功能导向），而不是"Skills / Agents / 已连接工具"（对象导向）

## ⚖️ 判例

**场景**：设计师提交了一个新的 Dashboard 设计。顶部放了 4 个大按钮（导入/同步/连接/设置），下方才是状态卡片。

**判定**：**违反原则 1，打回。**

**修改意见**：状态卡片提到最顶部；4 个大按钮降级为工具栏图标按钮，放在右上角。

# 原则 2 · 明确先于惊喜

> **Clarity before Delight**

## 📖 内涵

当"清楚的表达"和"惊艳的体验"冲突时，**永远选清楚**。

这不是说我们反对好看——而是**好看是结果，不是目标**。用户打开 App 是为了解决问题，不是为了看动画。

## 🎯 L1 依据

- 气质 = **冷静 × 工程精准** —— 这两个坐标都排斥"花哨"
- 反面参照 = **Notion / Adobe / 钉钉** —— 都因过度设计被排除
- 用户 = Alex —— "讨厌废话"是画像核心

## ✅ 正例

- **按钮文案**："同步全部"（动词 + 宾语，3 个字说清）
- **加载态**：直接显示进度 "2/5"，不做旋转粒子特效
- **数据更新**：新数字直接替换旧数字，不用 flip 翻牌动画
- **过渡动效**：160ms 淡入淡出，不做弹跳 / 缓动 / 视差
- **错误文案**："CodeBuddy 未连接" + 一个"检查路径"按钮

## ❌ 反例

- ❌ 按钮文案："立即开启你的同步之旅 ✨"
- ❌ 加载态：一个炫酷的 Lottie 动画，但看不出还要多久
- ❌ 数字更新：用 500ms 的 flip 动画——**好看但拖慢感知**
- ❌ 页面切换：3D 翻转 / 视差滚动 / 光标跟随粒子
- ❌ 错误文案："噢豁～好像出了点小问题呢 (｡•́︿•̀｡)"

## ⚖️ 判例

**场景**：开发者提交了一个同步成功的庆祝动画——绿色的勾从中心迸发粒子，持续 800ms。

**判定**：**违反原则 2，需修改。**

**修改意见**：绿色勾保留，粒子删掉；总时长压缩到 ≤ 300ms。  
**保留理由**：勾是"状态"的强化，粒子是"惊喜"的装饰——前者必要，后者不是。

**特例允许**：首次打开 App 的欢迎页、或极少数成就解锁场景（每年 ≤ 3 次），可以有稍长的动效。其它地方一律压缩。

# 原则 3 · 诚实先于友好

> **Honest before Friendly**

## 📖 内涵

**我们尊重用户的智商，胜过照顾他们的情绪。**

当产品出问题时（同步失败、路径找不到、配置冲突），**就老实说**——别用"小问题""遇到点麻烦""稍后重试"这类糊弄话术。

**用户是 Alex，不是需要哄的小孩。** 你糊弄他一次，他下次就不信你了。信任一旦丢失，产品就废了。

## 🎯 L1 依据

- 情绪诉求 = **安心 + 掌控感** —— 掌控感建立在"信息对等"上
- 气质 = **冷静克制** —— 反对客服式温柔
- 用户 Alex = 技术人员 —— 看得懂错误信息，讨厌被当小白

## ✅ 正例

- **失败提示**：「CodeBuddy 同步失败。路径不存在：`~/.codebuddy/skills/`。检查路径」
- **版本过时**：「需要更新。你本地版本 `v2.3.1`，工具里是 `v2.1.0`，差 3 次提交」
- **权限问题**：「无法写入。目录只读：`/opt/codebuddy/`」
- **网络问题**：「SkillHub 连不上。检查网络，或离线使用」

## ❌ 反例

- ❌ 「哎呀，我们遇到了一个小问题，请稍后再试 😅」
- ❌ 「网络开小差啦～」
- ❌ 「操作失败，请检查配置」（没说检查哪个、哪里错）
- ❌ 用模糊的"同步中..."状态一直挂着，实际上早就失败了
- ❌ 红色错误弹窗，但关闭后就永远找不到了（用户想复现问题都难）

## ⚖️ 判例

**场景**：设计师设计了一个"同步失败"的 Toast 提示——图标是哭脸表情，文案是「哎呀，同步好像没成功呢～」，3 秒自动消失。

**判定**：**违反原则 3，打回。**

**问题清单**：
1. 哭脸 Emoji → 卖萌，违反冷静克制气质
2. "好像"——不确定的措辞，让用户更慌
3. 3 秒自动消失 → 违反"诚实 = 信息留痕"（用户想回头看都找不到）

**修改意见**：
1. 图标改为红色感叹号（语义色 Danger）
2. 文案改为「同步失败：[具体原因]。[具体操作按钮]」
3. Toast 不自动消失，必须用户手动关闭；同时在"同步中心"永久留下失败记录

# 原则 4 · 克制先于全面

> **Restraint before Completeness**

## 📖 内涵

**宁可少做一个功能，也不做一个半成品。**

每当面对"要不要加上 XX"的纠结时，默认答案是 **"先不加"**。功能可以之后补，但一旦加了就很难减——这是产品膨胀的根源。

**我们的产品是抽屉，不是瑞士军刀。** 抽屉的价值在于"整理"，不在"什么都塞进去"。

## 🎯 L1 依据

- 隐喻 = **抽屉** —— 抽屉就该空出来，不是塞满
- 反面参照 = **中控台** —— 我们明确拒绝"主宰感"
- 差异化 = **轻量无侵入** —— 功能多 = 重 = 侵入

## ✅ 正例

- **首版只做 Skills 同步**：Commands / Agents / Rules 骨架已留，但**不做 UI**，等用户真的需要再做
- **不做协作功能**：本地优先，不做团队共享（那是另一个产品）
- **不做 Prompt 编辑器**：只管同步，不管内容——内容编辑交给用户的 IDE
- **不做使用统计图表**：Alex 不关心"这个 Skill 用了多少次"，只关心"是不是最新"

## ❌ 反例

- ❌ 「我们要不要加个"快捷导入 GitHub 仓库"？」—— 先不加，默认拒绝
- ❌ 「Dashboard 要不要加 4 个小部件？使用率、同步量、错误趋势、活跃度」—— 一个"全局新鲜度"就够了
- ❌ 「设置页要不要加 20 个开关做精细控制？」—— 先只做最核心的 3 个，其它用默认值
- ❌ 做到一半的功能挂上"Beta / 即将推出"字样 —— 不做就是不做，不搞期货

## ⚖️ 判例

**场景**：产品经理提议"Dashboard 加一个'本月同步次数'的趋势图表，让用户有成就感"。

**判定**：**违反原则 4，拒绝。**

**论证**：
1. 用户 Alex 的核心情绪诉求是"安心"，不是"成就感"——后者是游戏化产品的诉求
2. 趋势图本身不能推动任何决策（看到"同步了 100 次"后，用户能做什么？不能做什么）
3. 图表 = 像素密度 = 视觉噪声，违反 L1 "留白充足"气质
4. 一旦加了，以后还要维护、还要加筛选、加对比——技术债务起点

**替代方案**：如果真的想传递"你很高产"的正反馈，可以在**首次达到阶段里程碑**时给一个轻量的 Toast（"已同步超过 50 次 ✓"），一次性、不持久化。

## 🧭 冲突时如何仲裁

当 4 条原则之间出现冲突时，按这个顺序决定：

```
诚实先于友好  >  状态先于功能  >  明确先于惊喜  >  克制先于全面
    (信任)         (掌控)           (清晰)           (简洁)
```

**逻辑**：没有信任，其它都白谈；信任建立后，用户要的是掌控；掌控的前提是信息清晰；在清晰之上，再追求简洁。

**示例冲突**：
- "同步失败时，要不要弹窗？"
  - 克制说：不要弹窗（增加打扰）
  - 诚实说：必须醒目告知（不能藏着）
  - **诚实优先 → 给一个非阻塞的 Banner，但让它留痕到"同步中心"。**

## ⚖️ 走查用法（给评审人的参考）

**评审一个设计稿时，按顺序问 4 个问题：**

1. 打开这个页面，用户**先看到状态还是先看到按钮**？（原则 1）
2. 有没有**动效 / 装饰性元素**是"为了好看而好看"？（原则 2）
3. 错误态、空态、失败态，文案**是否诚实**？（原则 3）
4. 这个页面有没有**"能不能删"的信息或功能**？（原则 4）

**4 个答案都通过 = 通过评审。** 任何一个不通过 = 先改再评。

## 九、本层结论对下游的约束清单

| L2 原则 | 约束了 L3~L7 的什么 |
|---|---|
| 状态先于功能 | L3 首页必须是"状态仪表盘"而非"操作菜单"；L5 卡片的状态徽章必须在主视觉区 |
| 明确先于惊喜 | L4 动效 token 最长 ≤ 400ms；L5 禁用装饰性 loading 动画 |
| 诚实先于友好 | L5 错误组件必须包含"原因 + 操作路径"；L5 禁用卖萌 Emoji 和"哎呀/噢豁"等语气词 |
| 克制先于全面 | L3 首版页面清单 ≤ 5 个；L5 任何"Beta/Coming Soon"标记一律禁止 |
